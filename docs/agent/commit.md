# 커밋 컨벤션

- 형식: `<type>: <한글 설명>` — type은 `feat` / `fix` / `ci` / `test` / `docs` / `refactor`.
- 예: `feat: fetch_recent_logs tool 추가 — 전체 레벨 최신 로그 조회`
- 커밋은 **사용자가 명시적으로 요청할 때만** 수행. main 브랜치면 먼저 브랜치를 판다.

## 커밋 단위 — 논리적 변경 하나당 커밋 하나

- **하나의 커밋에는 하나의 논리적 변경만 담는다.** "기능 추가"와 "그 김에 정리한 버그 수정/미사용 코드 제거"는
  같은 작업 세션·같은 PR 안에서 나온 변경이라도 **서로 다른 논리적 변경이면 별도 커밋으로 나눈다.**
  - 좋은 예: `code-review`에서 발견된 버그 3건을 고칠 때 → 버그마다 별도 커밋 (`fix: A`, `fix: B`, `fix: C`).
  - 나쁜 예: "기능 추가 + 미사용 메서드 제거 + 오타 수정"을 전부 하나의 `feat:` 커밋에 몰아넣기.
- 판단 기준: 이 변경만 되돌린다면(`git revert`) 다른 변경에 영향을 주지 않고 깔끔히 되돌려지는가?
  아니라면 같은 커밋, 그렇다면 나눠야 할 후보.
- 순서: 먼저 전체 diff를 파악한 뒤 논리적 단위로 나눠 각 단위를 `git add <파일>`로 선택적으로 스테이징하고
  단위별로 커밋한다. `git add -A`로 한 번에 묶어 커밋하지 않는다.
- 이미 여러 논리적 변경이 섞인 채로 작업이 끝났다면, 커밋 직전에 diff를 다시 훑어보고 나눌 수 있는지 확인한다.
